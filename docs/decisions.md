開發過程中使用者拍板的決定，以及還在等待決定的事。`/day-start` 開工時讀、`/day-end` 收工時更新。
只記使用者做的決定；建議與評估放在日誌（`docs/journal/`）。

## 待決定

- `S0812_PT`（4 小時短班）目前 `work_fraction = 1`，總覽算 1 天上班：維持，或改成 0.5 天？
- 排班總覽：待審核的半天假，要不要也和已核准的一樣分上下兩段顯示（目前只顯示虛線框的假）？

- 員工能否主動對已核准的請假 / 加班送出「取消申請」（需新增狀態，由主管確認）？

## 已決定

- 2026-10-14｜開發日誌與判斷點放在 `docs/`（進版控）；`/day-end` 的備份源為 git + 資料庫，push 前先問｜換電腦、協作者都看得到進度
- 2026-10-14｜不做 i18n，需要其他語言時用瀏覽器翻譯｜約 750 段中文字串，內部系統維護雙語成本過高
- 2026-10-14｜`dim_shift_code.shift_name` 維持現有英文名稱，不改｜評估後決定不動
- 2026-10-14｜排班總覽：同一天部分上班、部分請假時，同一格分上下兩段同時顯示（依時間先後）｜原本只會擇一顯示
- 2026-10-14｜一天內「幾小時上班 + 幾小時請假」的結構改動（按時數請假、請假獨立成表）先不做｜現有半天 / 四分之一天已夠用，改動範圍大
- 2026-10-14｜主管取消已核准的請假 / 加班：先看逐日影響、原因必填（伺服器端也檢查）｜避免誤觸
- 2026-10-14｜核准後的調整只在主管手上；員工撤回只限待審核的單｜已生效的異動都要經主管並留紀錄
- 2026-10-14｜加班「送出申請」先跳確認彈窗；預覽與送出共用同一套檢查（含有沒有主管能審）｜防呆
- 2026-10-14｜提交班表每次送出都先預覽逐日結果，確認後才寫入；全有或全無（任一天失敗整批不寫，API 回 400）｜避免部分寫入、讓使用者先看到覆蓋了什麼
- 2026-10-14｜Agent 的上班班別（`SHIFT`）只能選自己的預設班別；休息、公務活動不限；其他角色不限｜避免 Agent 誤選班別
- 2026-10-13｜`fact_roster` 刪除 `full_name`、`office_code`、`team`、`brand`，一律 join `dim_employee`；不保留歷史的 team / office｜改員工資料要立即反映；既有資料是測試資料
- 2026-10-13｜`fact_roster` 複製自 `dim_shift_code` 的欄位（`status_group`、時間、天數）與舊欄位 `is_ot`、`ot_fraction` 不動｜天數與時段在寫入當下計算，保留快照較合理
- 2026-10-13｜排班總覽沒帶 `month` 時預設顯示當月；選「全年」時匯出與明細也是全年｜—
